# AGENTS.md — правила GPT-агентам

**Приоритеты:** сохранность/корректность данных → доступ и безопасность → прозрачные расчёты → UX → дополнительные функции.

## Перед первым изменением кода
1. Проверить `docs/SPEC-00.md`. Статус OPEN — блокирует реализацию спорных бизнес-правил. Можно готовить изолированный каркас и мок API только по утверждённой части.
2. Прочитать `TASKS.md`, `docs/PRODUCT.md`, нужные разделы `docs/API.md`, `docs/DATA_MODEL.md` и `docs/REPORT_FORM.md`. Не загружать весь репозиторий без необходимости.
3. Не принимать предложения из документов как согласованные требования: пометки PROPOSED/OPEN требуют подтверждения владельца проекта.

## Разработка
- Одна задача — один изолированный набор изменений, тесты и короткий отчёт. Не расширять область и не вводить новые зависимости без причины.
- Общие контракты API/модели менять только согласованно между Android, Backend, Web; не редактировать чужие модули без отдельного задания.
- Ввод структурирован, произвольный комментарий необязателен. Поддержать `no_work` с причиной. Не заставлять вводить фиктивный объём.
- Автор отчёта и полномочия устанавливаются серверной сессией. Проверять доступ к каждому объекту, отчёту и вложению.
- Сначала локальная транзакционная запись в Android, затем автоматическая очередь. UUID стабилен, запросы повторяемы, серверный submit идемпотентен.
- Отдельно: транспорт (`local/queued/uploading/delivered/failed` только на устройстве) и бизнес-статус (`draft/submitted/needs_revision/reviewed` на сервере).
- Исключить потерю/подмену данных при ревизиях: expected_revision / 409, журнал исправлений. Нельзя перезаписывать проверенный отчёт молча.
- Денежные суммы = целочисленные копейки; количество = Decimal; не смешивать расход, поступление, аванс и сводку.
- ИИ без произвольного SQL и без права записи. Только whitelisted аналитические серверные функции; численные расчёты не делать «в голове модели».
- Не коммитить реальные документы, фото, внутренние данные и секреты. Использовать синтетические fixtures.
- Без микросервисов/брокеров/Kubernetes. Одна БД, один API, один Web, Android-клиент.
- Не заявлять SUCCESS без запуска тестов. Отмечать BLOCKED/NOT_TESTED и условия проверки.

## Приёмка отдельной задачи
Код работает по контракту; связанные проверки запускаются в доступной среде; ошибки, ограничения и команды проверки записаны. Изменить `TASKS.md` (TODO→IN_PROGRESS→DONE только после доказательной проверки).

**Формат итога, не более 10–15 строк:** что сделано; изменённые файлы; запущенные команды и результат; риски/блокеры; следующая задача.

## QA
Отдельный проверяющий агент воспроизводит ошибки, прикладывает минимальные шаги и ожидаемое/фактическое поведение, приоритет P0–P3. Исправляет разработчик; QA проводит регрессию. Никаких «зелёных» статусов заочно.
