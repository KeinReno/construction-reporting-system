# CRS — live-demo readiness (4 ноября 2026, 11:00 МСК)

**Цель:** физический Android (рабочее APK, НЕ offline-demo) → HTTPS → единый FastAPI и единая БД на ноутбуке → desktop Web + mobile Web → проверка той же записи. Сборка и сервер должны быть проверены на самом ноутбуке; этот документ не подтверждает, что они уже установлены.

## Сетевая схема и предельные условия

```text
Android app (com.kaiden.construction, DEMO_MODE=false)
   | HTTPS, valid CA, endpoint https://<public-host>/api/v1
   v
trusted HTTPS ingress / outgoing srv.us SSH tunnel
   | -> 127.0.0.1:58494 on laptop (NOT 192.168.x.x)
   v
FastAPI + SQLite pilot [private data directory]
   | same origin
   +-- laptop browser http://127.0.0.1:58494/     (manager)
   +-- separate browser window / DevTools 390x844  (manager)
```

**Android жёстко требует HTTPS:** `HttpsEndpoint.normalize()` запрещает HTTP, а AndroidManifest запрещает cleartext. Поэтому хот-спот/общий Wi-Fi сами по себе не решают задачу. API в пилоте слушает только loopback; по LAN напрямую он не виден. В рабочем Android указывать полный адрес `https://<actual-host>/api/v1`, а в браузере — `https://<actual-host>/` или локальный `http://127.0.0.1:58494/`. Только существующий проверенный HTTPS-туннель/HTTPS reverse proxy. Не обходить TLS и не отключать проверку сертификатов.

**Привязка сервера к установке APK:** после первого входа endpoint фиксируется. Не перепривязывать инсталляцию с существующими черновиками. Перед повторной установкой/очисткой данных вручную проверить и сохранить важные черновики.

**Две страницы Web = один сервер:** оба окна должны открывать одну базу и одного руководителя. На `/?mode=employee` расположен отдельный веб-клиент сотрудника, на `/` — кабинет руководителя. Он не заменяет нативный Android.

## Подготовка ноутбука (приватные данные не трогать на GitHub)

### Быстрая установка нового пустого пилота

На Windows 10/11 с Python 3.12, Node.js/npm и встроенным OpenSSH из корня исходников выполните:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/demo/Install-LaptopHost.ps1 -DataRoot C:\CRS-Laptop
```

Скрипт один раз собирает Web, устанавливает зависимости Python, создаёт отдельную пустую SQLite БД, администратора с паролем из интерактивного ввода и выделенный ключ HTTPS-шлюза. Существующую папку он не перезаписывает. Откройте `C:\CRS-Laptop\START-HERE.txt`: сначала создайте в локальном Web тестовый объект, менеджера и бригадира с назначениями; затем `START-CRS.cmd` поднимет API/Web на ноутбуке и исходящий HTTPS-туннель. `STOP-CRS.cmd` его остановит. Для Android нужен **обычный**, не demo APK: введите адрес из `ССЫЛКА.txt` с `/api/v1`, затем логин и пароль бригадира. Ключ туннеля сохраняйте вместе с приватным runtime: адрес привязывается к нему, а Android закрепляет endpoint после входа. [srv.us описывает стабильный адрес по SSH-ключу](https://docs.srv.us/).

Это подготовка отдельного нового контура. Реальные архивные данные таким способом не переносятся; для их переноса нужна проверенная резервная копия. Успешная установка не подтверждает доступность HTTPS в мобильной сети и доставку отчёта: пройдите ниже физическую репетицию и `Test-LiveDemo.ps1`.

1. На исходном ПК остановить CRS и подготовить **консистентный** backup DB + uploads; не копировать работающую SQLite напрямую и не использовать архив релиза как замену данных. Сохранить оригинал/контрольную сумму/точку отката.
2. Для новой пустой установки получить исходники с `codex/laptop-host-20261104` после публикации ветки; для переноса реальных данных сначала выбрать и проверить отдельную согласованную интеграцию. Путь `B:\CRS-runtime` относится к старому ПК и **не гарантирован** на ноутбуке.
3. Для локального пилота выбрать приватный каталог ноутбука, например `C:\CRS-runtime`; перевести `config.json` с корректными абсолютными `code_root`, `web_dir`, `uploads`, `database_url=sqlite:///...`, `port=58494`. Проверить состояние БД и наличие данных **без изменения исходника**. Настройка `gateway` и выделенный ключ `gateway_ed25519` находятся только в приватном runtime.
4. Python 3.12: подготовить `.venv` и `backend/requirements.lock.txt`. Для последнего Web: `cd web; npm ci; npm run build`; при остановленном сервере перенести `web/dist` в отдельный приватный `runtime/web`. Изменение исходников само по себе не обновляет открытую приватную сборку.
5. Проверить роли: `foreman` привязан к объекту, `manager` имеет доступ к этому же объекту, нет путаницы между локальными, демонстрационными и настоящими учётными данными.
6. Из корня исходников запустить `powershell -ExecutionPolicy Bypass -File scripts/windows/Start-LocalPreview.ps1 -DataRoot C:\CRS-runtime` (путь заменить); **не ставить `-LocalOnly`**, если Android должен видеть HTTPS-туннель. Прочитать фактический адрес в `C:\CRS-runtime\ССЫЛКА.txt`. В новом пустом контуре пароль был задан интерактивно при установке; в прежнем перенесённом контуре может существовать приватный `ДОСТУП.txt`. Никогда не показывать пароль в публичном PR.
7. В PowerShell запустить `scripts/demo/Test-LiveDemo.ps1 -HttpsBase https://<actual-host> -WithAuth`. Интерактивный ввод учётных данных; preflight не отправляет отчётов и не меняет БД. С телефона через мобильную сеть **отдельно** открыть `https://<host>/ready` и выполнить вход в Android.

## Репетиция в 7 шагов

1. Desktop Web `/`: войти менеджером, открыть «Отчёты»/«Главная».
2. Второе окно `/`: открыть viewport 390×844 через DevTools, убедиться, что это тот же сервер. В каждом окне выполнить вход (session token хранится в памяти).
3. Android: открыть **обычный** «СтройКонтроль», а не «СтройКонтроль Демо». Ввести/проверить URL с `/api/v1`; войти как сотрудник; убедиться, что нужный объект виден.
4. Отправить уникально обозначенный тестовый отчёт; для первого smoke-теста можно без фото, затем повторить с одной тестовой фотографией. Не вводить выдуманные производственные показатели в реальную БД. Отметить точный client/report ID и receipt, дату смены.
5. Дождаться на телефоне **«Доставлен»** и квитанции: **«В очереди» не равно принят сервером**. Если WorkManager занят, не перезапускать/не удалять данные без диагностики.
6. На desktop Web нажать «Обновить», найти именно эту запись, открыть/проверить детали/фото. В mobile Web тоже нажать «Обновить» и открыть тот же report ID. **На текущем Web нет подтверждённой push/realtime-синхронизации**; ручное обновление нормально для демо.
7. После успешного основного сценария: руководитель возвращает на уточнение с причиной → Android исправляет → руководитель видит новую ревизию. Если этот дополнительный сценарий нестабилен, убрать его из встречи, а не скрывать сбой.

## GO / NO-GO для живой демонстрации

**GO** только когда после реального перезапуска на ноутбуке: `/ready` отдаёт 200; мобильный Android видит валидный HTTPS и проходит login, получает назначенные объекты; хотя бы один уникальный тестовый отчёт принят и имеет receipt; одна и та же запись и её фото видны в desktop и mobile Web; нет утечки приватных паролей и исходных вложений.

**NO-GO**: HTTPS недоступен с телефона; телефон использует demo APK; нет достоверной квитанции; ноутбук после перезапуска не поднимает API; не проверены ACL/фото. Без подмены выводов: показать архивную Web-ретроспективу и объяснить, что пилот Android→сервер ещё проходит сетевую приёмку.

## Демонстрация (короткий сценарий)

1. «Вот рабочее место бригадира; он отправляет факт смены». С телефона заполнить и отправить.
2. «Отчёт доставлен и попал на сервер ноутбука»; показать receipt.
3. В desktop Web нажать обновление, открыть нужный отчёт/фото, показать роль руководителя.
4. В mobile Web нажать обновление, открыть **тот же** отчёт; ID и содержание должны совпасть.
5. Кратко показать сводки по **подтверждённым** данным (исторические 94 записи — ретроспектива, не текущие просрочки).
6. «GPT пока не подключён: локальные аналитические сценарии работают, над GPT-слоем продолжается работа. Внешняя передача данных только после согласования». Не демонстрировать фальшивый ИИ-ответ.
