# REPORT_FORM — форма отчёта v0.2

**Статус полей:** техническая рекомендуемая схема, бизнес-обязательность требует SPEC-00 B01–B07. Не принуждать сотрудников заполнять вымышленные объёмы/время.

## Шапка
- `site_id`: объект (обязательно).
- `work_date`: дата работ в часовом поясе объекта (обязательно).
- `team_id` или подтверждённый состав (PROPOSED B01/B04).
- `shift_id` / `zone`: если настроены для объекта.
- `kind`: `work` или `no_work` (обязательно).
- Автор `author_id` определяется из авторизованной сессии, не из формы.

## Сотрудники и время
Выбор из справочника работников, плюс привлечённые работники с категорией/ролью по согласованию. Выезд, прибытие, время допуска — разные поля. Не принимать разницу этих времён за трудочасы без подтверждённой методики. Изменения состава во времени сохранять в истории.

## Работы
`work_entries[]`: UUID, тип из справочника, единица, числовой объём для количественного типа (Decimal и совместимая единица) ИЛИ статус выполнения для качественного, участок, заметка, фото. Несколько работ в одном отчёте. Тип «Другое» — с обязательным уточнением, пометить на последующую классификацию.
Для `no_work`: отсутствие `work_entries` допустимо, но требуется `no_work_reason`, при необходимости объект/инцидент простоя.

## Материалы
`material_entries[]`: справочник, количество, единица, движение `received` / `consumed`. Пустой список означает «не заявлено», а не автоматически нулевой расход. Покупка и потребление — разные записи.

## Деньги (включение в MVP требует B05)
`financial_entries[]` = `expense`, `funding_received`, `advance_issued` и др. из согласованного перечня. Сумма в копейках, дата операции и категория. Фото чека — вложение к операции. Сводные итоги не отправлять как новые транзакции. Подробности в FINANCE.md.

## Инциденты и планы
Явно указать «инцидентов не было» либо структурированный инцидент: категория (нет допуска, отсутствие материала, погода, техника, другое), интервал/длительность при наличии, пояснение. План следующего дня — отдельные необязательные пункты, не поручения в задачнике.

## Фото и комментарии
Фото относятся к отчёту, работе, инциденту либо денежной операции. На этапе сохранения проверяется доступность файлов; при submit сервер проверяет полностью полученные обязательные вложения. Свободный общий комментарий не обязателен и не заменяет обязательные поля.

## UX
Шаги: объект/дата → состав → работы или отсутствие работ → материалы/деньги → события → фото/комментарий → проверка/отправка. Секции компактные, условно раскрываются; сохранять черновик автоматически. Ошибки валидации показывать у конкретного поля. Отдельно видны состояние отправки и состояние проверки.
