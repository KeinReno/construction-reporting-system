# ARCHITECTURE — производственная схема v0.2

Android (Kotlin Compose + Room + WorkManager) ↔ HTTPS REST API (FastAPI) ↔ PostgreSQL; API также обслуживает приватные вложения, адаптивный Web (React/TS) и аналитические запросы. Внешний шлюз публикует только HTTPS API/Web; БД закрыта. Windows 24/7 на стороне заказчика. Обмен с Orion — будущий отдельный адаптер.

## Android: от нажатия «Отправить» до квитанции
1. Атомарно сохранить локальную копию отчёта, work_entry UUID, attachment UUID, файл и очередь.
2. Сеть доступна: идемпотентно POST draft по неизменному client_report_id. При пропаже ответа повторить; совпадающий ID без совпадающего содержимого → 409.
3. Отправить вложения, checksum; при обрыве повторять передачу. Никакой «доставлено», пока все обязательные фото не stored.
4. `submit` с expected_revision; сервер в транзакции проверяет данные/связи/фото и сохраняет submitted_at, receipt_id.
5. После чтения квитанции Android показывает «Доставлено». Если ответ потерялся, клиент проверяет состояние по ID вместо создания нового отчёта.
6. Отдельно менеджер проверяет отчёт; needs_revision запускает ревизию без перезаписи истории. Conflict 409 показывает выбор перечитать данные/повторить изменение без silent overwrite.

## Транспорт ≠ проверка
Локально: local/queued/uploading/retrying/delivered/failed. Серверный business_status: draft/submitted/needs_revision/reviewed. Нельзя «переотправить новый отчёт» при needs_revision: корректируется существующий и повышается revision.

## Время и аналитика
work_date = дата работ по TZ объекта; created/submitted/received_at — UTC. Фото EXIF не источник истины; времена выезда/допуска не равны фактическим трудочасам. Агрегировать quantity только по совместимым единицам, финоперации — по видам, ожидания — по сменным назначениям.

## Надёжность и безопасность
Транзакции, оптимистические ревизии, rate limit, ограничения размеров, файл сначала temp → sha256 check → атомарное сохранение. После перезапуска приложения очередь восстанавливается из Room. Android app-private storage; защиту локальных данных и политику хранения/отзыва доступа согласовать. ACL для каждого объекта и файла. Backup БД + вложений и регулярный реальный restore-test. Внешний HTTPS-туннель/реверс-прокси выбирать только после проверки целевой сети с VPN и без.

## ИИ
Read-only расчётные функции возвращают числа, фильтры, источники; LLM формирует объяснение. Нет ключа/провайдер недоступен — дашборд и обычные графики продолжают работать. Запросы и расходы ограничены.

## Избегаем
Микросервисов, отдельной синхронизации Web-БД, websocket как обязательного условия. Для 10–20 отчётов в день Web достаточно периодического обновления или refresh вручную.
