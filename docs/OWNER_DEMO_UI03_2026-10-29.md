# UI-03: архивная сверка и источники объекта

Состояние на 29/10/2026. Это локальный срез **демо владельца** на отдельной приватной SQLite-базе. Он не меняет общий контракт отчётов, статусы `submitted/reviewed`, импорт или Android. `docs/SPEC-00.md` остаётся PARTIAL; спорные производственные правила этим срезом не утверждаются.

## Поведение

- На главной «К сверке записей» открывает карточку неуточнённого объекта. Для каждой из трёх спорных архивных записей видны дата, краткое содержание, исходное сообщение и отдельная форма решения.
- Владелец должен явно выбрать «Относится к ПС Факел», «Не относится к ПС Факел» или «Недостаточно данных» и написать основание не короче 10 символов. Предыдущий выбор не подставляется в новую запись. Журнал показывает все версии с автором и временем; последнее решение определяет счётчик нерешённых записей.
- Решение сохраняется только в `owner_archive_reviews` приватной базы. Исходный отчёт, его объект, ревизия, бизнес-статус и аналитические расчёты не меняются. Подтверждение объекта в производственном импорте — отдельная задача после сверки.
- Карточка ПС Факел показывает указанные в сообщениях планы и отмеченные события с рабочей датой и переходом к исходному отчёту. План подписан как намерение, исполнение не подтверждается. Пустые поля не трактуются как нулевые показатели.

## Локальный API

- `GET /api/v1/owner-demo/reconciliation` возвращает историю по спорным `client_report_id` по возрастанию ревизии.
- `POST /api/v1/owner-demo/reconciliation/{client_report_id}` принимает `decision`, `reason`, `expected_revision`; запись добавляется транзакционно, устаревшая ревизия получает 409. Доступ разрешён только сессии конкретного владельца, указанного в приватных credentials. Ответы не кэшируются (`private, no-store`).
- Это demo-only путь в `scripts/demo/owner_max_real_app.py`, а не новый общий `/reports/{id}/review`. Android и основной Backend API его не вызывают.
