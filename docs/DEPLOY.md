# DEPLOY — Windows-сервер, внешняя доступность, сопровождение

**Пока неизвестны** версия/редакция Windows, CPU/RAM, диск, доступность Docker/служб, права, антивирус/файрвол, сетевые ограничения. Проверить до выбора способа установки (SPEC-00 B11/B12).

## Плановая схема
PostgreSQL и приватный каталог фотографий на сервере клиента; FastAPI и Web под TLS-шлюзом. БД не должна иметь публичного порта. Если используется внешний туннель/VPS, обосновать модель доверия, обновления и доступность без VPN в целевых сетях. Только исходящие подключения при необходимости и минимальные открытые поверхности.

## Чек-лист подготовки
1. ОС и обновления; учётная запись служб без избыточных прав; процесс автозапуска и рестарта.
2. Диск + прогноз роста фото (10–20 отчётов × среднее число снимков × размер × срок хранения), лимиты и очистка временных файлов.
3. HTTPS сертификат и тест из мобильных сетей/домашнего Wi-Fi (с VPN и без), DNS/домен/туннель, правила firewall.
4. Переменные окружения/секреты вне Git, защищённый первичный admin, rate limit, журнал ошибок без личной информации.
5. Консистентный backup PostgreSQL + вложений на отдельное устройство/место, шифрование копии по политике; тестовый restore и RPO/RTO.
6. Логирование статусов очереди, здоровья API, ошибок БД и места на диске; инструкция при недоступном сервере.
7. Обновления с миграциями, резервной копией и rollback, хранение релизной APK.
8. Юридические договорённости: роли по защите данных, доступ разработчика, срок хранения и обслуживание после приёмки.

## Проверки
Отправка отчёта при стабильной сети, затем при потере сети. Перезапуск Windows между вложением и submit. Проверка авторизации, чужих объектов и фотографий. Дашборд с iPhone/Windows и доступ без обязательного VPN. Реальное восстановление резервной копии.

Не хранить реальные сетевые адреса/админ-пароли/вложения/доступы клиента в публичном репозитории.
## Реализованные инструменты обслуживания PR #2

Для новой БД в `backend/`: `python -m alembic upgrade head`. `init-db` оставлен для разработки. Для исходной bootstrap-БД PR: остановить API, сделать копию, сверить таблицы и столбцы с migration 0001; **только после совпадения** `python -m alembic stamp 0001`, затем `python -m alembic upgrade head`. Не stamp произвольную БД. Legacy timestamps остаются NULL. Не применять downgrade для отката приложения без плана сохранения новых данных.

Для backup/restore задать `DATABASE_URL` и `UPLOAD_DIR` приватно, выполнить из `backend/`:
```bash
# Предусловие: API остановлен, никакие записи/загрузки не идут.
python -m app.backup backup /private/new-snapshot --service-stopped
python -m app.backup verify /private/new-snapshot
# Затем переключить DATABASE_URL на НОВУЮ пустую БД,
# UPLOAD_DIR — на новый/пустой каталог. Не затирать действующий контур.
python -m app.backup restore /private/new-snapshot --service-stopped
```
Для PostgreSQL нужны pg_dump/pg_restore совместимой версии в PATH; адрес/пользователь/пароль передаются процессу через environment. Команды используют стандартные host/port/user/password/database URL; сложные SSL/socket настройки требуют отдельной проверки окружения. Backup копирует только зарегистрированные фото, сверяет SHA256 и создаёт manifest. Restore проверяет manifest до записи. Копии содержат чувствительную БД и медиа; права/шифрование/носитель определяются политикой заказчика. Флаг service-stopped — подтверждение оператора, не автоматическое обнаружение Windows-службы.

Restore не обещает транзакцию между PostgreSQL и файловой системой. При ошибке восстанавливать заново в новый чистый контур; действующую БД не трогать. После восстановления проверить вход, источники и фотографии, затем менять endpoint/запускать службу. Production Windows-service/reverse proxy, домен, restart policy и регламент копирования остаются B11/B12 и полевой приёмкой.
