Справочник доступен в отдельном Web-разделе, в формах и производственной аналитике. При переименовании старые имена остаются зарезервированными, включая регистр, и не переносят исторические отчёты к новому виду.

Табель: один человек/дата — одно начисление, 500000 копеек за рабочий день независимо от часов, стандарт8ч. Командировка — отдельный признак. Ручные доплаты и штрафы требуют причины; суммы, ревизии, идемпотентность и before/after аудит фиксируются сервером. Это не выплаты и не денежный расходный журнал. Владелец задаётся явно через owner_user_id/CRS_OWNER_USER_ID и остаётся ограничен назначениями объектов.

Боковая панель Web и мобильного Web содержит сохранённую переписку по отчёту/дате и ИИ. Источник ответа ИИ открывается в переписке. Совпадение даты подписано отдельно от подтверждённой связи. ACL применяется к отчёту и всему сохранённому корпусу. При смене фильтра старый источник сбрасывается.

## Ограничения и установка

Физический Android, ноутбук заказчика, рабочая миграция/восстановление и внешняя эксплуатационная приёмка не выполнены заочно. Живая база/фото не редактировались. Android debug/release и unit-тесты уже прошли GitHub Actions; отдельная физическая проверка не заменяется эмулятором. Локально нет JDK/SDK/Gradle.

Автоматической синхронизации с MAX и гарантированного iframe живого MAX нет: панель работает с сохранённой перепиской, источниками и доступным ИИ. Переписка целиком автоматически провайдеру не передаётся. Нужные для живого MAX доступы/поддерживаемый API отсутствуют; существующие корпуса независимы от MAX.

Табель заполняется владельцем явно; похожие исторические имена автоматически не объединяются, фактические начисления из них не создаются. Для командировки без работ можно сохранить worked=false, business_trip=true и ручную доплату. Один день распределяется на выбранный объект; несколько отчётов не создают несколько оплат.

До обновления остановить API, сделать приватную проверяемую копию БД+uploads, применить alembic upgrade head, указать UUID владельца, затем обновить Web и Android. Подробно: WINDOWS_INSTALL.md и API.md. Откат рабочих данных — восстановлением копии, не удалением новых таблиц.

Незавершённые старые эксплуатационные задачи LIVE-LAPTOP-01/DEMO-LAPTOP-01 остаются IN_PROGRESS; критерии и команды в TASKS.md. Новые поля и табель не закрывают открытые B11/B12/B14.

## Дополнительные регрессии на повторном CI

После основного прогона независимо воспроизведён случай двух отчётов одного объекта/даты (work + no_work): сводка объекта считала рабочий день и день без работ одновременно. В rest_days объекта теперь исключены даты с работами. Добавлен API-тест; независимая QA повторила три синтетических сценария и API-регрессию (1PASS). Итоговый focused-прогон production/owner/migrations: **20 PASS**, 106.03с.

Повторный Backend CI42131268008 выявил несовместимый PostgreSQL-клиент на runner: pg_restore отправил `SET transaction_timeout`, которого нет у сервера16. Это реальный отказ восстановления; тест не отключался. Клиент pg_dump может читать более старый сервер, но восстановление его вывода в более старую версию не гарантируется ([официальная документация PostgreSQL](https://www.postgresql.org/docs/17/app-pgdump.html)).

Backup/restore теперь читают major сервера и до операций БД подбирают совпадающие pg_dump/pg_restore: сначала PATH, затем стандартные каталоги установленной версии. При отсутствии совместимого инструмента операция прекращается с указанием CRS_PG_BIN_DIR. Явный override использует только заданную папку, без скрытого fallback. Пароли остаются только в окружении дочернего процесса. Прикладные Python/JS-зависимости и службы для этого не добавлены.

Тесты несовпадения major, выбора установленного16 вместо default17, SQLite backup/restore и runtime-package: **5 PASS**, 11.10с. Независимая QA дополнительно проверяет, что несовместимость не запускает dump/restore и не меняет исходные файлы. Реальное восстановление PostgreSQL после этого исправления должно подтвердиться заключительным CI в PR7; старое успешное выполнение не подменяет новый результат.


В следующем реальном CI42132563753 защита корректно остановила backup до создания дампа: runner вообще не содержал клиент16, а PATH предлагал более новую версию. Поэтому Backend workflow явно устанавливает **postgresql-client-16** в одноразовом Ubuntu-runner и задаёт CRS_PG_BIN_DIR. Это требуемый клиент уже используемого сервера16, не новая зависимость приложения и не ослабление проверки. Итоговый реальный restore-drill проверяется повторным CI; тест не пропускается и ошибка не маскируется.


CI42133081423 показал, что ubuntu-latest уже выбирает Ubuntu26.04.1, где стандартный apt не содержит postgresql-client-16. Backend runner закреплён на поддерживаемом Ubuntu24.04 с явной установкой клиента16 ([официальный пакет Ubuntu](https://packages.ubuntu.com/noble/postgresql-client-16)). Это делает среду воспроизводимой; production-код и проверки backup/restore не ослабляются.
